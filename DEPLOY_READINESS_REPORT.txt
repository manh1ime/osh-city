ПРОВЕРКА ГОТОВНОСТИ ПРОЕКТА К DEPLOY НА TIMEWEB CLOUD
Дата проверки: 01.09.2026

ИТОГ
----
Проект не готов к гарантированному первому деплою на чистый VPS с чистой
PostgreSQL-базой без дополнительных действий.

При этом приложение в целом подготовлено для запуска на Timeweb Cloud VPS:
есть Dockerfile, docker-compose.yml, production-пример переменных окружения,
Prisma и инструкция TIMEWEB_DEPLOY.md. TypeScript-проверка и production-сборка
проходят успешно.

КРИТИЧЕСКИЙ БЛОКЕР
------------------
1. [ВЫПОЛНЕНО] Начальная миграция создания схемы добавлена в
   prisma/migrations/20260829000000_init.

В репозитории есть миграции:
  - 20260829000000_init
  - 20260830152000_reservation_preorders
  - 20260830154500_staff_night_shift
  - 20260831120000_reservation_code_unique

Начальная миграция содержит CREATE TABLE для Restaurant, StaffUser, Reservation,
Order и остальных базовых таблиц. Последующие миграции изменяют эту схему.

docker-entrypoint.sh запускает:
  npx prisma migrate deploy

На новой базе эта команда создает базовую схему и последовательно применяет
все последующие изменения. Проверка выполнена на чистом PostgreSQL 16:
`npx prisma migrate deploy` успешно применил все 4 миграции.

ОБЯЗАТЕЛЬНО ПЕРЕД ДЕПЛОЕМ
-------------------------
2. Создать на VPS файл .env.production на основе .env.production.example.

Нужно задать реальные значения:
  - POSTGRES_PASSWORD: длинный случайный пароль;
  - AUTH_SECRET: отдельный случайный секрет минимум 16 символов, лучше 32+;
  - HASH_SALT: другой отдельный случайный секрет;
  - NEXT_PUBLIC_APP_URL: настоящий HTTPS-адрес сайта;
  - POSTGRES_USER и POSTGRES_DB: согласованные значения базы.

Файл .env.production нельзя коммитить в Git или включать в Docker-образ.
После создания рекомендуется выполнить chmod 600 .env.production.

3. Подготовить VPS Timeweb Cloud.

Нужны:
  - VPS с Ubuntu 24.04 или совместимой Linux-системой;
  - публичный IPv4;
  - установленный и работающий Docker Engine и Docker Compose;
  - SSH-доступ с sudo;
  - открытые только SSH, HTTP и HTTPS порты;
  - домен с A-записью на IP VPS.

Инструкция этих действий уже находится в TIMEWEB_DEPLOY.md.

4. Настроить HTTPS reverse proxy.

docker-compose.yml публикует приложение только на 127.0.0.1:${APP_PORT}.
Это корректно для VPS, но снаружи сайт будет доступен только после установки
Caddy, Nginx или другого reverse proxy и получения TLS-сертификата.

В репозитории нет Caddyfile или Nginx-конфигурации. Это не блокер, если proxy
настроить вручную по инструкции TIMEWEB_DEPLOY.md, но без этого не будет
публичного HTTPS-сайта и корректных production QR-ссылок.

5. Определить способ первичного заполнения базы.

В production seed автоматически не запускается, что правильно для защиты
существующих данных. Для новой базы нужно отдельно решить, нужны ли стартовые
данные, и при необходимости выполнить npm run db:seed внутри контейнера.

Если переносится существующая база, требуется заранее подготовить и проверить
backup/restore, а затем применить миграции командой prisma migrate deploy.

ПРОВЕРЕНО УСПЕШНО
-----------------
6. npm run typecheck завершился успешно.

7. npm run build завершился успешно. Next.js собран в режиме standalone,
   необходимом для текущего Dockerfile.

8. package-lock.json присутствует, поэтому Docker-сборка использует npm ci.

9. Dockerfile устанавливает OpenSSL, генерирует Prisma Client, собирает Next.js
   и запускает приложение через docker-entrypoint.sh.

10. PostgreSQL не публикуется наружу в docker-compose.yml. Приложение подключается
    к базе по внутреннему имени сервиса db.

11. .env, .env.production, backup-файлы и dump-файлы исключены из Git и/или
    Docker-контекста.

ПРЕДУПРЕЖДЕНИЯ И РЕКОМЕНДАЦИИ
-----------------------------
12. В production-сборке есть предупреждения ESLint о пяти местах с обычным
    <img> вместо next/image. Это не мешает деплою, но может ухудшить оптимизацию
    изображений и LCP.

13. В проекте нет автоматического CI/CD workflow. Для ручного VPS-деплоя это
    допустимо. Для регулярных обновлений желательно добавить проверку
    typecheck/build и контролируемый процесс обновления контейнера.

14. Нужно настроить регулярные PostgreSQL backup вне контейнера и хранить хотя
    бы одну копию за пределами VPS. Команды для этого приведены в
    TIMEWEB_DEPLOY.md; автоматическое расписание в репозитории не настроено.

15. Перед боевым запуском нужно вручную проверить главную страницу, редиректы
    /manager и /staff/orders, QR-меню обоих филиалов, заказы, бронирования,
    предзаказы, роли сотрудников и отмену брони.

РЕКОМЕНДУЕМЫЙ ПОРЯДОК ДЕЙСТВИЙ
------------------------------
1. [ВЫПОЛНЕНО] Создать полноценную начальную Prisma-миграцию и проверить ее на
   чистой PostgreSQL-базе.
2. Закоммитить миграцию в репозиторий.
3. Создать .env.production с настоящими секретами и доменом.
4. Настроить VPS, DNS, firewall и HTTPS reverse proxy.
5. Запустить docker compose --env-file .env.production up -d --build.
6. Проверить логи, /api/health и пользовательские сценарии.
7. Настроить резервное копирование и только после этого считать деплой
   production-завершенным.

ЗАКЛЮЧЕНИЕ
----------
Для деплоя на Timeweb Cloud VPS инфраструктурная заготовка проекта есть, но
первый запуск на чистой базе нельзя считать готовым из-за отсутствия начальной
миграции Prisma. После добавления этой миграции, заполнения production
переменных, настройки домена/HTTPS и backup проект можно разворачивать.
